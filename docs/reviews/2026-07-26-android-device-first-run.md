# R-12(2026-07-26)设备侧首跑 —— R-5/R-6/R-8/R-9/R-10 在 arm64-v8a 上复测

**评审对象:** 前六道门(R-5..R-11)全部在 macOS/JVM 上取得,本次首次把同一套判据搬到真实
Android 运行时执行。
**判据来源:** 各门自己的原判据,一字未改地搬过来 —— 这正是本次评审的方法:**判据不动,看谁不过。**
**结论:** 22/22 绿,但**其中一门是靠换模型才过的,另外两处是真实缺陷**。

设备:`nl_gateD_api35` 模拟器,arm64-v8a / API 35 / totalMem 5926MiB。
执行:`scripts/push_device_models.sh` + `scripts/run_device_gates.sh`。

> **范围诚实声明(放在最前面):** 一台模拟器不是设备总体。本次能证明的是"端侧全流程在
> arm64 上数值成立",不能证明的是多 OEM 一致性(R-9 遗留)、真实存储 I/O、真实 CPU 热降频。
> 凡是本次没量到的,下面逐条写明,不用"应该没问题"顶替。

## 1. 最重要的一条:R-5 判据没过,换了模型而不是改判据

int8-transformer 导出(桌面侧 R-5 的结论模型,95.8 MiB)在 arm64 上**两条断言同时失手**:

| 断言 | 判据 | macOS fp32 | 桌面 int8 | **arm64 int8** |
|---|---|---|---|---|
| 说话人不变性 DTW cost | ≤0.18 | 0.1714 | 0.1773 | **0.18323 ✗** |
| 金标准嵌入余弦(最差 clip) | ≥0.985 | — | 0.986–0.992 | **0.98297 ✗** |

**关键是先搞清这是什么性质的失败。** 把 0.18323 送进随包的 `calibration.json`,accuracy 仍是
**95.00**,与 macOS fp32 逐位相同;曲线上要走到 cost **0.1864** 才会给出不同的分数。也就是说
**不变性没有坏,余量坏了** —— fp32 时代离第一个 accuracy 拐点还有 0.0155,int8 吃掉 0.0027,
arm64 再吃 0.0055,只剩 **0.0032**。

这一步很容易走错成"既然分数没变,就把判据放宽到 0.185/0.982"。没有这么做,理由是:**两条只
因为量化恰好落得好才成立的阈值不是阈值**。放宽之后,R-5 此前所有数字都不再描述任何东西,而
下一次导出、下一次 ORT 升级、下一颗 OEM 的 kernel 都能把它推过拐点,届时表现为"学习者被告知
78 而不是 82",不会表现为错误。

于是走计划 §7 早已写明的 no-go 阶梯:**退 fp16**。实测(同一设备、同一次运行):

| | int8-transformer | **fp16(已采用)** |
|---|---|---|
| 说话人不变性 | 0.18323 ✗ | **0.16917 ✓**(优于 macOS fp32 的 0.1714) |
| → 校准后 accuracy | 95.00 | 95.00 |
| → 余量 | 0.0032 | **0.0172** |
| 金标准余弦 | 0.98297..0.98716 ✗ | **0.99006..0.99680 ✓** |
| 成对代价最差 Δ(vs macOS) | 0.01183 | **0.00930** |
| 吞吐(10.75s 音频,两次运行) | 427–497 ms / 21.6–25.2× 实时 | 842–879 ms / **12.2–12.8× 实时** |
| 体积 | 95.8 MiB | **139.7 MiB** |

(**只有时间是抖的,数值全部逐位复现** —— 两次运行的不变性、四个余弦、四个成对代价、Gate E 的三个
余弦都到最后一位相同,变化只在墙钟(模拟器共享宿主 CPU,±15%)。所以上表吞吐给区间而非单点,
但比值稳定在 **1.8–2.0×**。单句路径实测 12.7–13.1× 实时,3s 句子约 231–234 ms,NFR-3「秒级」宽松。)

代价:包体 891.3 → **935.1 MiB**(仍在 asset pack 1.5GB 上限内,余 590 MiB);编码吞吐约减半
(3s 句子 231–234 ms,NFR-3「秒级」仍宽松);R-8 峰值 PSS 713 → 892 MiB(预算 3500;713 是换装前那次
运行量的)。
**用户已就此拍板选 fp16**(记录于本次会话),`ModelCatalog.SSL_ENCODER` 与
`INSTALL_TIME_BYTES` 已改,`ModelRegistryTest` 的体积 pin 随之更新 —— 那个 pin 正是靠失败提醒
了这次改动,按设计工作。

### 1.1 fp16 兜底本身是坏的,两层坏法,都只有设备能发现

阶梯写了 fp16 兜底,导出脚本也确实产出了 `w2v2_base_69_fp16.onnx` —— 但它**从来没有被加载过
一次**。脚本当时只断言了文件大小,并把 parity「推迟到设备」。推迟 parity 和推迟「能不能打开」
是两件事,而当时两件都推迟了。

**第一层:导出根本载入不了。**

```
Type (tensor(float16)) of output arg (/model/encoder/Cast_1_output_0)
of node (/model/encoder/Cast_1) does not match expected type (tensor(float))
```

`onnxconverter_common.float16` 把该 Cast **产出**改成 fp16,却没改声明它类型的 `to` 属性,ORT
在选 kernel 之前的类型检查阶段就拒收。改用 ORT 自己维护的同一 pass
(`onnxruntime.transformers.float16`)解决。

**第二层:桌面能载入,设备仍然拒收 —— 而且是另一个原因。**

```
Failed to find kernel for com.microsoft.Gelu(1) ... implemented only for
(tensor(float),) but the node in the model has (tensor(float16))
```

图里**没有** Gelu,只有 17 个 `Erf`。融合发生在 ORT 的**载入期优化器**里:EXTENDED 级别把
Erf 形状的 GELU 重写成 contrib op,而桌面 ORT 有它的 fp16 kernel,**裁剪过的 Android 构建没有**。
即失败不在我们导出什么,而在运行时从中推导出什么 —— 所以桌面侧的载入测试原理上不可能抓到它,
只有设备能。

把 `Erf` 放进 `op_block_list` 即可:两侧插 Cast 打断融合模式,GELU 留在 fp32(数值上本就该留)。
用 `SessionOptions.optimized_model_filepath` dump 优化后的图核对:**contrib op 归零**(int8 那份
是 17 Gelu + 28 DynamicQuantizeMatMul + 9 SkipLayerNormalization)。代价是其余融合一并失去,
即上表 12.2–12.8× 实时里有一部分是**这份导出**的代价而非 fp16 本身的 —— 如实记录,不粉饰。

`scripts/onnx_export_spike.py` 现在**断言 fp16 能载入**,兜底不再是"需要它那天才发现是坏的"。

## 2. `:core-audio` 两个真实缺陷(不是测试问题)

R-9 桌面侧只验到重采样器;解码器是设备侧首次执行,两个缺陷都在这里。

**① 立体声下混错了 √2 —— 每一路视频参考音都低 3.01 dB。**
`toMono` 按 `channels` 取算术平均,而 libswresample 的 `layout=mono` 做的是**能量守恒**重矩阵,
即 `(L+R)/√2`。直接测 ffmpeg 的矩阵证实:(0.5,0.5)→0.707107、(0.5,0)→0.353553、(0.5,−0.5)→0。
表现为我们的解码比 `ffmpeg -ac 1` 整体轻 1.41343 倍,把这一个标量除掉后两者吻合到 49.3 dB ——
**整个偏差是电平,不是波形**。

**为什么下游一个都没报警,值得精确陈述而不是当运气:** `AudioPreproc.frameDb` 是
`amplitude_to_db(ref=np.max)`(相对最响帧);`WordDiff.stressPos` 返回 RMS 包络 argmax 的**位置**
且平坦判据是相对的;CMVN 把每个嵌入维度归一化。三者都尺度不变,所以 Gate E 的 cost 只动
0.003、accuracy 动 0.00。**但尺度不变是当下消费者的性质,不是保证** —— Silero VAD 有训练出来的
绝对灵敏度,而 AudioRecord 学习者路径(单声道、不下混)会保持正确,于是只有视频来源的参考音悄悄
低 3 dB。已修,并**单独 gate 电平**(`|gain−1|<0.01`),因为只有直接检查才抓得到它。

**② seek 之后解码器吃掉第一帧,请求的区间开头不存在。**
mp4/AAC seek 到 1.000 s,首个输出时间戳是 **1.0217 s** —— 在请求点**之后**。FR-8 的回放区间按词
边界切,这就是被削掉的辅音起音,且下游无法察觉。加 `PRE_ROLL_S = 0.1`(约 4 个 AAC 帧)回退起
点,`DecodedAudio.startS` 的「≤ 请求点」契约才真正成立;调用方按 `startS` 裁剪。

## 3. 三处判据/测量方法上的返工(方法论,不是数字)

**① 整数对齐不够,必须做分数样本对齐。** FFmpeg 在**重采样之前**按 edit list 裁掉 AAC 的 2112
样本 priming,而 2112 × 16000/44100 = **766.2** —— 输入侧整数、输出侧分数,两条 16 kHz 栅格差一个
任何整数移位都消不掉的零头。而这个零头在样本域并不小:δ 样本的移位对频率 f 的分量约花掉
`2·sin(πfδ/fs)`,0.2 样本 @3 kHz 已是 −12 dB。第一版测出 10.7 dB SNR,把纯粹的时基偏移读成了
解码器失真。加窗 sinc 分数移位后:AAC 49.2 dB、Opus 50.3 dB、seek 47.7 dB。

**② Gate E 判据 ① 的 0.995 不能原样搬到设备 —— 但这条结论的适用范围被 §1 的换装改窄了,如实分开写。**
那个 0.995 是桌面上**换重采样核 + fp32 编码器**量出来的(0.9983–0.9998)。**int8 编码器下它确实不成立**:
量化是阶跃函数,亚百分之一的输入变化可以跨过舍入边界,R-5 量到同一 int8 导出对 fp32 在**完全相同波形**
上只有 0.983–0.987 —— 要求两个不同解码结果穿过它之后吻合到 0.995,比编码器对自己跨精度的吻合度还高。
换装前那次运行实测 cos 0.9888–0.9928,**低于 0.995,靠噪声底那一支才过**。

噪声底的构造:把参考自身只施加已测扰动(增益/分数移位)再过一次编码器得到 `controlCos`,解码器不为
这条底线以上的差异负责。**fp16 换装后,判据 ① 恢复为直接达标,噪声底那一支不再是通过路径**——
本次实测 AAC cos **0.999895**(底线 0.999998)、Opus **0.999956**(0.999996)、seek **0.999803**
(0.999135),全部远高于 0.995。也就是说 §1 那 43.9 MiB 顺带买回了 Gate E 的判据原义。

结论按此分层:`cos ≥ 0.995 || cos ≥ controlCos − 0.002` 的**析取保留**,但它现在是**休眠的兜底**而非
现役判据 —— 保留的理由是它记录了"这条线为什么可能不适用",一旦日后换回量化编码器或换 ORT 版本,
失效方式会立刻被这一支接住并在日志里显形,而不是表现为一门莫名其妙的红。
→ **遗留项:`golden/device/manifest.json` 里 `emb_min_cosine: 0.995` 仍是个裸常数**,读 manifest 的人
看不到析取和噪声底的存在(目前只在测试代码的注释里)。已在本次补上说明字段。

**③ 一条从来没跑过的测量,报了它没测的数。** `install_time_set_is_present_and_hashes_match_the_catalog`
打印 `SHA-256 over 935.1 MiB took 0 ms (Infinity MiB/s)` —— marker 会跨运行存活(harness 故意不
卸载),于是首跑之后每次 `verifyAll` 都从 marker 直接返回,而这行日志正是它本该产出的 NFR-3
warmup 数据点。`Infinity` 是唯一露出来的破绽。现在先删 marker 再计时,并**结构性断言**(断言
marker 确实不在了)而非用时间做代理 —— 第一版改法用了 `ms > 1000`(「935 MiB 的 SHA-256 不可能
一秒内完成」),当场被证伪:模拟器命中宿主 page cache,424 ms / 2205 MiB/s。**对没量过的存储猜下限,
正是最初那个 bug 的成因。** 冷哈希数值因此**不可用作 warmup 设计依据**,需真机 UFS/eMMC 数据。

## 4. 一个非算法的坑,值得单独记:native 库在 test APK 里等于没有

11 个测试在 class-init 阶段全灭:

```
UnsatisfiedLinkError: dlopen failed: library "libonnxruntime4j_jni.so" not found
```

而 `unzip -l` 显示三个 `.so` 都在 —— 在**错误的 APK** 里。六个 core 模块当时挂在
`androidTestImplementation` 下(理由是 `:app` 还是 Phase-4 空壳,不该声明尚未使用的依赖)。这不是
AGP 允许的选择:instrumentation 把 test APK 的 **dex** 并进被测应用的 classloader,它的 `lib/`
**不以同样方式合并**,所以 test APK 里的 native 库不在应用进程的 `dlopen` 搜索路径上。

而且这本来也正是 Gate D 要测的东西:**"一个进程同时持有所有 session 的峰值 RSS"是应用进程的性质**,
session 必须按应用将来加载它们的方式加载。已改为 `implementation`。
