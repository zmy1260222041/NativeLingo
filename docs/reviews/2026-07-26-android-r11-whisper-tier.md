# R-11(2026-07-26)Whisper 档位 —— tiny.en 能不能替掉 base.en

> 这不是一道新门,是 **Gate F(R-10)对另一个档位的重跑**。
> 关联:`docs/PRD.md` FR-2(转写+句/词切分)、FR-6(词级定位)、FR-8(A/B 回放)、FR-11(音素诊断)、
> NFR-3(性能)、NFR-4②(包体)。前置:`docs/reviews/2026-07-26-android-gate-f-asr-text.md`。
> 脚本:`scripts/asr_text_parity.py`(本次加了 `--tier`,入库)。
> 语料:`videos/7.1.mp4`(CBS 新闻,636.1s,金标准 1944 词 / 164 句)。策略固定 `vadwin`/int8(R-10 定的 Android 可行路径)。

## 起因

R-10 实测 whisper base.en int8 是 **159.8MB**,越过 Play 基础 APK 的 150MB 压缩上限,
所以 whisper 必须换分发方式。摆给用户的三条路是:安装时 asset pack / 首启下载 / **换 `tiny.en` 档位**。
用户选了换档。**换档是未测量的动作** —— R-10 的三条判据是在 base.en 上量出来的,
换一个档位必须自己再过一遍,否则转写文本的错误会顺着四条下游传导(见 R-10 §"为什么需要一道门")。

## 结论:**tiny.en 三条判据都过 —— 但不建议采用**

判据是过的,所以这不是一次"失败"。不建议的理由是**余量**和**分歧的结构**,两条都不在判据里。

| vadwin / int8,同一语料同一策略 | base.en | tiny.en | Gate F 判据 | 判定 |
|---|---|---|---|---|
| int8 体积(encoder + decoder) | 29.1 + 130.7 = **159.8MB** | 12.9 + 89.9 = **102.8MB** | — | tiny 省 57MB |
| 归一化 WER vs 金标准 | 4.01% | **4.89%** | ≤5% | ✅ 余量 **0.11pp** |
| 终止标点分歧(仅在两侧词相同处统计) | 1.65%(31/1883) | **1.88%**(35/1858) | ≤2% | ✅ 余量 **0.12pp** |
| 练习单元数(仅文本驱动,金标准 159) | 158(−0.6%) | **162**(+1.9%) | ±5% | ✅ |
| 分歧区域数 | 49 | 56 | — | +14% |
| 636s 全片转写(桌面 arm64,4 线程) | 38.2s 墙钟 / 142s CPU | **22.9s / 82s** | — | tiny 快 **1.67×** |

### 不建议的第一个理由:0.11pp 的余量不是余量

R-10 已经写明两件事,合起来就否掉了这点余量:

1. **判据是事后定的** —— 定在"最好的策略实测值 + 余量",不是从既有指标推出来的先验。
   用它给 base.en 打分是自洽的;用它当另一个**模型档位**的合格线,是把它拉到设计意图之外。
2. **只有一段语料** —— R-10 原话:「单一素材足以证明分歧是局部替换而非系统性错误,
   **不足以给出 WER 的置信区间**」。

一条事后定的线、一段语料、0.11pp 的距离 —— 这不构成"过了"。base.en 的 4.01%(余量 1.0pp)
才是判据能承载的那种通过。

### 不建议的第二个理由(决定性):分歧的结构退化了,而 R-10 判 PASS 恰恰依赖这一条

R-10 判 PASS 的核心论证是:**分歧「全是局部替换/增删,没有一处是整段崩坏」**,
所以"文本不作为平台间的对等目标"是安全的。把两侧的多词分歧(参考侧 ≥2 词、且不是纯分词/标点差异)
逐条摊开,这条论证在 tiny.en 上不再成立:

**base.en 的 6 处多词分歧,没有一处产生非词:**

```
'the 250 ,000,'  -> '250,000,'                 分词(金标准更差)
'51 %'           -> 'fifty one percent'        书写规范,两种都对
'seven, two,'    -> '7-2,'                     书写规范
'stride and'     -> 'strident'                 听错,但仍是英语词
'How did'        -> 'Out of'                   听错,但仍是英语词
'to do that.'    -> ''                         删除
```

**tiny.en 新增的 5 处里,有 2 处是非词、1 处把主播名整个揉烂、1 处凭空造了个数字:**

```
'tariff ruling, in essence' -> 'terror-frueling, and, as since'   ← 'terror-frueling' 不是词
'decide? In factically,'    -> 'to side. infatically'             ← 'infatically' 不是词
'Tony DeCoupe. The'         -> 'Tonya Colpola.'                   ← 主播名,每条片段开头都出现
'the million, the 250 ,000,'-> '2,250,000,'                        ← 造出一个原文没有的数字
'to our'                    -> 'or a'
```

**为什么"非词"是不一样的错误。** MMS 强制对齐器**没有拒绝路径** —— 给它
`terror-frueling` 它就必须把这串字符铺到真实音频上。于是:

- **FR-2/FR-6**:该 span 内每个词的 `[start,end]` 变成任意值 —— 不是"偏了几十毫秒",是没有对应关系。
- **FR-8**:A/B 回放按这些边界切,点某个词会放到别处的音频。
- **FR-11**:canonical 音素来自文本,`terror-frueling` 的音素说话人从未发出。
  (这一条有防线:MDD 的 canonical 自拟合门控会拟合不上而 `return ""` 静默降级 —— 见 R-10 决定 3。
  **但另外三条没有防线。**)

`stride`→`strident` 这类听错不会造成这种后果:词还在原位,边界仍然对应真实发音。
**所以 4.01%→4.89% 这 0.88pp 不是均匀变差,它买来的是一类新的、下游没有防线的错误。**

### tiny.en 真正值钱的地方:快 1.67×

这一点不该被上面否掉。R-10 的第二个发现是「int8 一点也不更快,**换档位才是那根杠杆**」,
本文把这句话量出来了:**38.2s → 22.9s 墙钟(CPU 142s → 82s)**。桌面上这只是"都很快",
手机上是"能不能忍"的区别 —— 而 NFR-3 要求单句分析秒级、首次转写可后台。

## 顺带否掉一条:量化 embedding 表省不下来

R-10 指出 base.en decoder 之所以只量化 1.5×(196.5→130.7MB),是因为 51864×512 的
token embedding 表按 fp32 保留。本文核实了这一点并试了那条显然的杠杆:

| | base.en decoder | tiny.en decoder |
|---|---|---|
| fp32 全部 initializer | 195.4MB | 113.5MB |
| 其中 `textDecoder.token_embedding.weight` | **106.2MB(54.4%)** | **79.7MB(70.2%)** |
| 出厂 int8 文件里该表的 dtype | **仍是 fp32,占 130.7MB 的 81%** | 同 |

`quantize_dynamic(op_types_to_quantize=["MatMul","Gather"])` 的结果是**变大**:

| | 出厂 int8 | 加量化 Gather |
|---|---|---|
| base.en decoder | 130.7MB | **157.2MB** |
| tiny.en decoder | 89.9MB | **109.8MB** |

原因清楚:该表有三个消费者 —— `Gather`(token 查表)、`Identity`、`Add`。
量化只给 Gather 那条路加了一份 26.6MB 的 uint8 副本,**fp32 原表因为另外两个消费者还得留着**,
于是两份都在。要真省下这 106MB,得改图让 tied 输出投影也吃 int8 表 ——
**那是在动 logits 路径**(整个输出分布),风险与收益不对称,本次不做。
如果日后包体成为硬约束,这是一条已经定位清楚、但需要单独一道门的路。

## 建议

**base.en 保留为发布档位,走安装时 asset pack;tiny.en 保留为低端设备的运行期降级档。**

推荐 asset pack 而不是换档,理由是我上一轮给用户摆选项时**低估了 asset pack 的边际成本**:
wav2vec2(95.8MB)+ MMS(338.6MB)+ espeak(302.9MB)= 737MB **无论如何都要下载机制**,
这套机制是必须存在的。whisper 搭这趟车的增量成本≈0,而换档要付上一节那类错误。
这是对上一轮框架的一处修正,如实记下。

两档并存的代价很小(注册表里两份文件),换来的是把 tiny.en 的 1.67× 用在真正需要的地方:
按 `ActivityManager.MemoryInfo` / 实测首次转写耗时在低端设备上降档,而不是让所有设备都吃精度损失。
**降档的判据留到设备侧定** —— 桌面上量不出"多慢算太慢"。

## 没做的事

- **仍然只有一段语料**(R-10 的同一项欠账)。0.11pp 的余量之所以不可信,一半原因在这里。
- **未测 tiny.en fp32**。R-10 已证明 int8 对转写的损失是噪声级(0.11pp),没有理由单独为 tiny 再验。
- **未测设备侧**。同 R-10:桌面 arm64 与手机 arm64 的 int8 kernel 可能不同。
- **两档并存的降档判据未定**(见上,需设备数据)。
