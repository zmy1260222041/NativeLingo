## 0. 为什么判据先写、数字后填

R-10 与 R-11 留下的教训是:**事后定判据会让余量失去意义**。R-10 的三条判据是写完
`:core-asr` 才定的,导致 R-11 在评估 tiny.en 时只剩 0.11pp 余量却无法判断这个余量是否
可接受 —— 因为判据本身是照着已有结果凑的。

本评审因此在**任何实现开始之前**把七道门的数字判据写死。后续实测只允许填数字与记录
是否通过,**不允许因为过不了而放宽阈值** —— 那等于作废本文档。

## 2. 七道门

### G1 —— 意思传达判准可用性

| 项 | 内容 |
|---|---|
| **判据** | 手标 ≥200 条学习者应答(四个 tier 各 ≥50 条),确定性槽位匹配对「意思是否传达到」的 **precision ≥0.85 / recall ≥0.70** |
| **为什么是门** | 用户自己指出「评估算法决定了游戏可玩性的上限」。判不准,NPC 的施舍就是随机的,整个正反馈机制失效 |
| **方法** | 每条应答由人工标注 `delivered: bool`,与槽位匹配结果比对。precision 优先于 recall:**误判「传达到」比误判「没传达到」更伤** —— 前者让用户学到错的表达,后者只是让他再说一次(而 §5 设定里再说一次没有代价) |
| **状态** | 待实测 |

### G2 —— ASR 对 L2 短语的可用性

| 项 | 内容 |
|---|---|
| **判据** | `base.en` 在 infant / toddler 级短句(2–6 词、L2 口音、可能语法不全)上的**关键词召回 ≥0.85** |
| **为什么是门** | 槽位匹配的输入是转写文本。**转写丢词 = 判准链路从源头断掉**,G1 再准也救不回来 |
| **不可外推的既有数字** | R-10 实测的归一化 WER 4.01% 是在**新闻播报**语料上测的(演播室音质、母语播报腔、完整句子)。本模块的分布是 L2 口音、短句、语法不全、可能有环境噪声 —— **同一个模型在两个分布上的表现不可互推**,必须单独测 |
| **方法** | 只统计 `slots.accept` 中出现的关键词是否被转写命中,不统计整句 WER —— 整句 WER 不是本模块的消费方式 |
| **降级路径** | 若不达标,候选方向:(a) 换更大的 whisper 档位(需重新核 NFR-3 延迟与体积);(b) 在 `accept` 集合里补入常见转写错形。**不允许**放宽判据 |
| **状态** | 待实测 |

### G3 —— 场景库覆盖度与贴合度

| 项 | 内容 |
|---|---|
| **判据** | 场景 **≥40 个**,覆盖需求金字塔**前三层**;人工评「日常常见度」与「需求贴合度」(1–5)**均 ≥4.0** |
| **为什么是门** | 用户明确写「需求场景是否足够常见/足够贴合需求,决定了本游戏对语言学习帮助的上限」。这是与 G1 并列的两个上限之一 |
| **方法** | 每个场景的 `provenance.rationale` 与 `provenance.frequency_basis` 必须填写,评审时逐条核。空 `provenance` 的场景不计入 40 个 |
| **状态** | 待实测 |

### G4 —— 分级词表授权与体积

| 项 | 内容 |
|---|---|
| **判据** | 所选词表的许可**明确允许随包再分发**(逐条核对,含闭源/商业分发场景);解压后体积与首次启动延迟记录在案,不得违反 NFR-3 |
| **为什么是门** | 项目已有先例:选 Piper `libritts_r` 时逐条核过 CC-BY 4.0 并写进 NFR-5。**授权未核实前不得写进实现计划** |
| **附带影响** | 词表体积会改动分发体积数字。若显著,需同步修正 PRD 中相关体积记录 |
| **状态** | 待核实 —— 词表尚未选定,§7.1 的四级切分点因此也尚未确定 |

### G5 —— 云端审核的隐私边界

| 项 | 内容 |
|---|---|
| **判据** | 三条同时成立:① 代码级审计确认出站 payload **只含** NFR-6 白名单字段(转写文本 + 场景摘要 + 词汇等级);② 开关关闭时**零出站请求**(抓包验证,不是读代码推断);③ 离线 / 超时 / 异常三条路径**均静默降级且游戏可完整完成** |
| **为什么是门** | NFR-6 是全 App 唯一的联网例外。边界必须**可验证**,不能靠「实现时注意」。一次越界出站就作废 NFR-1 对用户的全部承诺 |
| **方法** | ② 必须抓包。R-12 的教训 ③ 是「一条绿着的测量可能在报它没测的数」—— 读代码确认不发送 ≠ 实际不发送 |
| **明确禁止出站的** | 音频、录音、照片、设备标识,以及任何 Speaking / Memorizing 模块的数据 |
| **状态** | 待实测 |

### G6 —— 模块隔离

| 项 | 内容 |
|---|---|
| **判据** | 进入 / 离开游戏模块**不改变** Memorizing warmup 的 stage 与进程 RSS;Speaking 的 accuracy / fluency 数值**逐位不变** |
| **为什么是门** | `core/memorize_warmup.py:37` 的 generation-token 生命周期假设**单一 owner**。两个模块各自 `start()` / `release()` 会互相拆台 —— `release()` 存在的唯一理由就是 Florence + Qwen 约 950MB 放不下 |
| **设计上为何应当通过** | 游戏的本地依赖是 whisper `base.en`(已在产)+ Parselmouth + 可选 Piper / SSL,与 Florence / Qwen **无共用**。但「设计上应当」不等于「实测通过」,仍须测 |
| **状态** | 待实测 |

### G7 —— 表达效果分的教学有效性

| 项 | 内容 |
|---|---|
| **判据** | 两条同时成立:① **单调性** —— 同一场景下「表达更完整 / 更自然」的应答得分**不低于**粗糙应答;② **包容性** —— 语法不完美但意思传达到的应答**不得被判为失败**(即不得落入无物资区间) |
| **为什么是门** | 这一条是**产品意图的数值化**,不是锦上添花。§2 设定的全部心理功能(婴儿身份、包容 NPC、怕用错词)如果在分数上不成立,叙事就是空的 |
| **方法** | 构造成对样本:每个场景一组「粗糙但达意」/「完整且自然」的应答对,断言单调;另一组「语法错但达意」的应答,断言均有物资产出 |
| **顺带定的事** | fluency 的绝对阈值(`num_pauses` / `total_pause_s` / `articulation_rate`)在本门的样本上定 —— 现有 `score_b.fluency_from_features` 的 GAM 权重是与 DTW 路径联合拟合的,**不可拆出单个分量复用** |
| **状态** | 待实测 |

## 4. 已知设计张力（如实记录）

1. **确定性槽位匹配结构性地奖励不了创造性表达。**它奖励的是「命中预设 `accept` 集合」。
   云端审核正是为补这个缺口而存在 —— 但它默认关闭,因此**离线玩法的可玩性上限由
   G3(场景覆盖度)与 G1(判准质量)决定**,而不是由审核质量决定。这意味着 G1 / G3
   过不了的话,开启云端审核也救不回来。

2. **离线时没有语义兜底。**本地 Qwen2.5-0.5B 判断力不足,不承担审核裁判;离线路径只有
   槽位匹配。**这是有意的取舍,不是遗漏。**

3. **场景库是人工内容,规模是长期成本。**G3 的 ≥40 个场景是持续投入,不是一次性交付。
   场景库停止增长时,模块的学习价值随之封顶。

4. **G1 的 precision / recall 判据本身依赖手标集的质量。**200 条手标应答如果不覆盖真实
   学习者的粗糙表达形式,G1 会给出偏乐观的数字。手标集的构造方式需在实测时一并记录。

## 5. 结论

**计划中。**七道门的判据已在实现之前固定。放行条件:

- **G1 / G2 / G3 为 P0 阻塞门** —— 任一不过,模块的核心价值不成立,不得进入实现。
- **G4 为前置门** —— 词表授权未核实前,FR-20 的四级切分点无法确定。
- **G5 为 FR-23 的放行门** —— 不过则 FR-23 单独不实现,FR-22 的纯离线玩法不受影响。
- **G6 / G7 为实现期验收门。**

数字回填后更新本文档与 PRD §7 对应条目。
