# 物品获得与使用

> **状态**：首轮可玩实现完成；最终表现与独立人工体验验收待完成（详见 R-30）
> **作者**：用户 + Codex
> **最后更新**：2026-09-06
> **实现支柱**：先行动，后开口；生存有压力，表达无羞耻；关系就是生存资源；小聚落，深模拟
> **所属系统**：`design/gdd/systems-index.md` “物品与资源”

## 概述

“物品获得与使用”系统把 NPC 对话成交产生的抽象资源，转化为玩家能在世界中看见、
取得、携带、放置和使用的实际物件。NPC 只决定交付的物品及数量；食物与饮品可现场食用或
打包带走，日常用品必须带回住处、放入对应位置后使用。每种物品独立定义用途、效果、使用地点、
放置目标和是否消耗，使关系带来的生存资源通过世界行动产生实际意义，而不是由对话结果直接修改
隐藏数值。该系统连接对话、背包、住所、生存需求和存档；HUD 只提供选择与结果反馈，不拥有物品状态。

## 玩家幻想

核心幻想是通过交流获得由自己支配的生存资源。玩家通过行动、表达和关系取得具体物品，
并自主决定何时、何地、以何种方式使用。食物和饮品可以现场消费，也可以打包留到更需要的时候；
毯子、零件等日常用品则要带回住处，放到适合的位置改善长期生活条件。每件可携带、可保存、
可放置和可使用的物品，都是“关系就是生存资源”的可见结果；玩家对资源的取舍与安排，体现其逐渐
掌握自身生活的成长。

本系统不取消数值增益玩法，但不拥有词汇增益。词汇成长来自独立发生的 NPC–NPC 社会对话与观察流程，
并经过 `heard → spoken → used` 的异步阶段，在之后的玩家–NPC 交流中发挥作用。生存物品只在一次资源交流
完成后接收交付结果，不同时触发观察扩词、词级练习或词汇数值结算。

这里的隔离指**物品事件不推进词汇状态**，不是禁止后续服务交流使用已学词汇。
玩家在真实交流中使用先前观察、练习过的词，仍可由原词汇系统独立确认 `used`；是否取得或使用生存物品不参与这一判定。

## 详细设计

### 核心规则

#### 1. 交易只决定交付，使用才产生效果

1. NPC 服务对话的语音成交路径只有同时满足以下条件才可提交交易：NPC 已具名同一具体库存物品并明确作出交付/接单承诺，
   对话服务将该轮标记为完成行为，且同一回复的 NPC 语音已经播放结束。只有“食物”“零食”“饮品”“零件”等泛类词、
   问句、库存外物品、玩家中途走开或语音尚未结束时均不得结算。
2. 成交后只输出唯一交易 ID、来源 NPC、来源服务点、确切物品 ID、确切数量和交付档位。确切数量是物品系统的唯一数量源；
   交付档位只用于反馈、审计和一致性校验，物品系统不得根据档位再次计算或放大数量。
3. 交易结果不得直接修改食物、温暖、精力、住所设施或词汇状态。
4. 物品系统对每个交易 ID 只结算一次。重复回调只返回已有结果，不重复创建物品。
5. 整批交付必须原子成功或原子失败，不允许少生成部分物品却把交易标记为完成。
6. 交付成功后，物品先出现在柜台、托盘或 NPC 递交位上，进入“柜台待领取”状态；不自动进入背包。
7. 只有运行时明确标记语音不可用、网络失败或未激活时，`gesture_fallback` 才可跳过不存在的语音播放门禁；它仍须由服务点
   确定一个具体库存物品、写入确切数量 1 并产生唯一交易 ID。首轮无语音实现以玩家明确手势命令触发同步柜台交付，
   世界投影随后显示该物件；不等待不存在的语音或动画完成回调。有语音能力时普通手势不得创建交易。
8. 交易的确切数量必须与同一库存预留记录完全一致，并落在该奖励方式和档位允许的上限内；库存不足可以使 `generous`
   的确切数量低于 2。预留缺失、数量不一致或超过档位上限均视为协议错误：创建 0 件、回滚预留并记录诊断，不得自行重算。

#### 2. 物品类别定义默认规则，具体物品可收紧规则

| 类别 | 柜台可选动作 | 携带后可用地点 | 住处要求 | 使用后状态 |
|---|---|---|---|---|
| 食物 | 现场吃 / 打包 | 任意安全、非对话状态 | 无 | 消耗一份，应用该食物自身效果 |
| 饮品 | 现场喝 / 打包 | 任意安全、非对话状态 | 无 | 消耗一份或一次容器使用次数 |
| 住所耐用品 | 只能打包 | 不可在野外使用 | 必须放入命名位置后启用 | 留在住所可见，持续或在特定行为时生效 |
| 安装组件 | 只能打包 | 不可在野外使用 | 必须放到兼容设施后安装 | 转为设施安装进度，物品实例终结 |
| 住所消耗品 | 只能打包 | 不可在野外使用 | 必须先放入兼容容器或设施 | 在住所使用时扣减数量或剩余次数 |

类别只是默认行为。每种物品必须独立定义稳定物品 ID、类别、数量单位、堆叠上限、携带占用、
现场消费权限、允许使用地点、住所位置标签、消耗方式、效果类型与效果值、是否可收回、是否可转交、
是否会在昏倒时损失、唯一性规则和表现身份。未被物品定义明确允许的行为一律不可执行。

#### 3. 食物与饮品

1. 交付两份时，玩家可以逐份处理：两份现场消费、两份打包，或一份现场消费一份打包。
2. 现场消费是玩家的明确选择；成交、NPC 递出物品或玩家拿起物品都不得自动恢复需求。
3. 打包只改变物品的容器表现和所在位置，不产生任何生存效果。
4. 打包食物和饮品可在任意安全状态中使用。“安全状态”至少要求玩家不在对话、录音、奔跑、跳跃、
   昏倒、日切、模态界面或其他不可中断动作中。纵向切片的封闭判定为：角色只在 `idle` 或 `walking`、双脚着地、
   没有更高优先级交互时可开始使用。首轮操作在主线程同一命令内验证并提交；短动作仅是提交后反馈，不跨帧持有 `item_using`。
5. 需求已满且该物品的所有实际效果都为零时，系统阻止消费并保留物品；只有部分效果溢出时，结算可接收部分并
   完整消耗一份，事前提示会发生浪费。
6. 纵向切片默认不启用腐坏、保质期或食物品质随时间衰减。

#### 4. 日常用品

1. 日常用品不提供野外使用按钮或被动增益，也不因进入住处自动生效。
2. 玩家必须把物品携带回自己的住处，对具有明确语义的位置执行放置。本系统使用床铺、加热器、电力设备、洗漱位等
   命名位置，不提供网格、角度旋转或任意地面自由摆放。
3. 位置错误、容量不足或已被占用时，物品仍留在携带位，住所状态不变；系统不自动替换已有物品。
4. 放置和使用是两个可见步骤。例如，毯子先放到床铺，再“铺好”后修改睡眠结果；加热器零件先放入维修位，
   再安装后推进设施修复。
5. 耐用品生效后仍留在住处可见。若定义允许拆下，必须先原子撤销对应效果，再返回携带位。
6. 安装组件成功后转为设施状态；物品实例不得再被重复结算。完成的唯一设施不再接受或触发无用组件交付。

#### 5. 携带、堆叠与物品条

1. 携带容量按类别分开：食物/饮品使用少量消费品位，日常用品使用独立的住所用品位。各类容量由可调参数定义，
   不使用重量、任意形状格子或自动整理谜题。
2. 只有物品 ID、剩余次数、品质、保存状态和使用规则完全相同的物品才能堆叠。
3. 打包时先填充兼容的未满堆叠，再申请新携带位。玩家每次选定的数量必须全部装入或全部留在柜台；系统不静默装走一部分。
4. 容量不足时，玩家可改为现场消费、选择更小打包数量、放下其他允许放下的物品，或稍后回柜台领取。
5. 随身物品条只在玩家按住对应输入时出现，松开后隐藏。它是世界交互的选择器，不是全屏背包管理界面。
6. 实例按每份一个稳定 ID 保存，堆叠仅是容量计算上的兼容分组，不合并来源。水壶有两次使用次数且每壶占一位、不可堆叠，
   避免喝一次后因剩余次数不同拆堆而超出容量。住所领取箱允许暂存/领回携带物；不提供野外随意丢放。

#### 6. 服务点库存与奖励单调性

1. 库存按“服务点 + 具体物品”定义，不对所有 NPC 硬编码统一的“每日一次”。
2. 每项库存明确采用每日补充、有限数量、唯一交付或显式无限之一。例如，日常食物可每日补充，毯子可按住所床铺唯一交付，
   加热器零件只补足未完成的修复需求。
3. 柜台待领取、携带中、住所中和已安装的物品都计入有限或唯一供应判定，不得因玩家未拾取、已消费或移动物品而复制不应重复发放的物品。
4. 现有表达档位由语言交互系统拥有，物品系统只接收 `none / sparse / generous / fallback` 结果，不读取原始发音或地道度分数。
5. 每种物品必须明确奖励方式：
   - **数量型**（食物、饮品、普通消耗品）：`none = 0`、`sparse/fallback = 1`、`generous = 2`，高档增加同款物品数量。
   - **唯一权益型**（每个住所只需一件的耐用品）：`none = 0`，其余有效档位均为 1，高档不复制无用的第二件。
   - **需求封顶型**（安装组件）：先按数量档位得到意向数量，再以未完成的设施缺口封顶。
   物品系统不自动把高档换成“高级物品”、放大单份效果或产生通用货币。
6. `none` 不创建物品、不消耗有限库存、不损伤需求、关系或任务，并保留免费重试。

#### 7. 常规失去、转交和旧档迁移

1. 昏倒时只有“携带中”且物品定义允许损失的普通物品参与损失。每次最多从确定性排序第一的合格堆叠扣除 1 个数量单位，
   对应单位进入“已损失”终态，保留账本，不删除审计记录。柜台待领取物、住所物品、已安装物、唯一物、关系礼物和任务保护物不损失。
2. 损失选择必须确定性排序，依次使用物品损失优先级、取得时间和实例 ID，便于无界面测试复现。
3. “携带中 → 已转交”只对物品定义白名单中的目标开放。旧的给 Rowan 送水内容可作为非主线互动保留，但只能转交被明确允许的饮品。
4. 旧存档中的 `berries` 每单位迁移为 `food_legacy_berries`，`scrap` 迁移为 `component_alloy_part`，`water` 迁移为
   `drink_bottled_water`；这些是迁移兼容 ID，不得随展示名称改动。已保存的需求数值原样保留，不因迁移生成物品而再次恢复。
   `heater_repaired` 迁移为 `facility_home_heater` 的已完成状态。
   容量内旧物迁入携带位，超量部分进入 `home_storage` 住处领取箱；不截断旧物总量。存档升级为 v5，临时文件写完后原子替换。
5. 纵向切片不提供物品出售、拆解、通用合成、通用货币兑换、自由建造或无限设施升级。

### 状态与转换

每个可支配物品都由稳定实例记录表示；世界模型只是该记录在当前场景的表现，不是状态源。

| 当前状态 | 玩家/系统动作 | 下一状态 | 必要条件 |
|---|---|---|---|
| 不存在 | 提交已成交交易 | 柜台待领取 | 交易 ID 未结算；库存已保留；整批可创建 |
| 柜台待领取 | 现场吃/喝 | 已消费 | 物品允许现场消费；效果可完整提交 |
| 柜台待领取 | 打包 | 携带中 | 物品允许打包；所选数量能全部装入 |
| 携带中 | 吃/喝 | 已消费 | 食物/饮品允许随身使用；玩家处于安全状态 |
| 柜台待领取 / 携带中 | 喝一次多次容器 | 保持原状态 | 剩余次数减 1 后仍大于 0；最后一次才进入已消费 |
| 携带中 | 存入住处领取箱 | 住处存放中 | 玩家靠近 `home_storage`；不产生使用效果 |
| 住处存放中 | 领回 | 携带中 | 对应类别携带位足够；整批成功或不移动 |
| 携带中 | 放置 | 住处已放置 | 玩家位于自己的住处；目标标签兼容且有容量 |
| 住处已放置 | 铺好/启用耐用品 | 住处生效中 | 物品和位置匹配；住所接受效果 |
| 住处已放置 | 安装/使用一次性用品 | 已应用 | 物品和位置匹配；住所/设施状态修改成功 |
| 住处已放置 | 收回 | 携带中 | 定义允许收回；物品未不可逆使用；携带位足够 |
| 住处生效中 | 停用 | 住处已放置 | 定义允许停用；效果可撤销 |
| 住处生效中 | 拆下并收回 | 携带中 | 先撤销效果；定义允许拆下；携带位足够 |
| 携带中 | 转交允许目标 | 已转交 | 物品与目标都在白名单；目标系统已接受 |
| 携带中 | 昏倒损失 | 已损失 | 物品允许损失；被确定性规则选中 |

“已消费”、“已应用”、“已转交”和“已损失”是终态。未列出的转换均为非法转换。除旧档迁移外，
禁止“不存在 → 携带中”跳转；禁止日常用品从柜台或携带状态直接生效。

### 与其他系统的交互

| 系统 | 输入给物品系统 | 物品系统输出 | 所有权边界 |
|---|---|---|---|
| 游戏状态与时间 | 当前日/时间、日切、昏倒、存档时机 | 物品变化事件、可保存快照 | 时间与领域操作排序由游戏状态拥有；物品系统拥有物品生命周期 |
| NPC 服务对话 | 已通过具名承诺、完成行为与同轮语音结束门禁的交易 ID、来源、物品 ID、确切数量、交付档位 | 交付成功/重复/失败 | 对话拥有会话和成交判定；确切数量为权威值，档位只作反馈元数据；对话不拥有物品、需求或住所状态 |
| 服务点库存 | 库存预留、补充策略、唯一性约束 | 交付提交/回滚、已拥有查询 | 服务点拥有可售/可给数量；物品系统拥有已交付实例 |
| 世界交互接口 | 对物品、交付位和住所位置的交互意图 | 可用动作、成功/失败结果、表现投影 | 世界节点只表现并转发命令，不拥有物品状态 |
| 生存需求 | 当前值、上限、可接受效果量 | 实际应用量或拒绝原因 | 需求系统拥有需求值与昏倒阈值；物品只提交效果请求 |
| 住所 | 住所身份、位置标签/占用、设施和睡眠状态 | 放置、启用、撤销、安装请求 | 住所拥有位置拓扑与设施结果；物品系统拥有仍存在的物品实例 |
| HUD | 玩家选择的现场消费、打包数量、物品、放置或使用意图 | 只读物品、容量、动作和结果投影 | HUD 不拥有交付、背包、物品或效果状态 |
| 保存与继续 | 版本化纯数据与迁移结果 | 实例、位置、数量、状态、剩余次数、交易结算记录 | 存档层只序列化，不判断物品规则 |
| 任务/NPC 关系 | 显式转交目标与接受结果 | 转交成功/拒绝 | 只是转交白名单的软依赖，不可通过普通 NPC 交互删除任意物品 |
| 词汇系统 | 无 | 无 | `heard → spoken → used` 完全独立；物品交付不观察、不复读、不发词汇奖励、不迁移词汇状态 |

存档中的物品记录至少包含：稳定实例 ID、物品定义 ID、数量、生命周期状态、来源交易 ID、来源服务点、
当前容器/位置、住所位置 ID、剩余使用次数、已应用标记，以及已结算交易 ID 集合。所有引用使用稳定字符串或数字；
不存入 Node、Resource 对象或场景路径。

## 公式

本章只计算可交付数量、携带容量、实际物品效果与设施进度。表达档位由语言交互系统按已有的 40/70 阈值产生；
本系统不读取连续分数，不重新定义阈值。公式中的效果量、容量和设施需求值都来自物品/设施定义或可调参数；示例数字是
无界面测试向量，不是正式平衡值。

### 可交付数量

The `offer_quantity` formula is defined as:

`q_offer = min(q_intended(b, r, g), available(s, i, t))`

其中：

- 数量型：`q_intended = {none: 0, sparse: 1, fallback: 1, generous: 2}[b]`
- 唯一权益型：`q_intended = 0 if b = none else 1`
- 需求封顶型：`q_intended = min(q_band(b), floor(max(0, g_required - g_current - g_committed) / g_per_item))`

**Variables:**

| 变量 | 符号 | 类型 | 范围 | 说明 |
|---|---|---|---|---|
| 表达档位 | `b` | enum | `none/sparse/fallback/generous` | 语言交互系统的已结算离散结果 |
| 奖励方式 | `r` | enum | `quantity/entitlement/need_capped` | 具体物品定义的奖励方式 |
| 服务点 | `s` | stable ID | 已定义服务点 | 供应物品的柜台或服务位 |
| 物品 | `i` | stable ID | 已定义物品 | 玩家在本次成交中选定的具体物品 |
| 时刻 | `t` | number | 当前领域时间 | 用于每日补充或其他补充规则 |
| 档位意向数 | `q_band` | int | `0–2` | 数量档位映射 |
| 设施所需进度 | `g_required` | int | `> 0` | 设施定义拥有 |
| 当前进度 | `g_current` | int | `0–g_required` | 住所/设施系统拥有 |
| 已交付未安装进度 | `g_committed` | int | `0–g_required` | 柜台待领、携带和已放置组件可贡献的进度 |
| 单个组件进度 | `g_per_item` | int | `> 0` | 组件定义的进度贡献 |
| 当前可预留数量 | `available` | int | `0–+∞` | 库存策略扣除已提交和已预留后的结果 |
| 交易确切数量 | `q_offer` | int | `0–2` | 库存预留成功后写入交易的唯一数量源 |

**Output Range:** 纵向切片中为整数 `0–2`。在库存条件相同时，高档输出不小于低档。唯一权益可以使两个有效档位同为 1，但不得出现高档反而更少。

**Example:** `generous` 请求同款食物，可用库存为 5，则 `q_offer = min(2, 5) = 2`。`generous` 请求每个住所唯一的毯子，且唯一权益尚未领取，则 `q_offer = 1`。

服务点必须先预留 `q_offer`，再把它作为交易的确切数量。需求封顶使用向下取整，组件/设施数据还必须保证从初始进度到
`g_required` 的所有合法剩余缺口都能被兼容组件贡献整除，避免产生无法填满的尾差。物品系统只原子创建该数量，不得再用档位乘一次。
同一交易 ID 重复提交时创建 0 份并返回首次结果。

### 服务点可用库存

The `available_stock` formula is defined as:

- 每日补充：`A = max(0, L_daily - D_today - R_active)`
- 有限供应：`A = max(0, L_finite - D_life - R_active)`
- 唯一交付：`A = 1` 仅当唯一键未预留且从未提交，否则 `A = 0`
- 显式无限：`A = +∞`

**Variables:**

| 变量 | 符号 | 类型 | 范围 | 说明 |
|---|---|---|---|---|
| 每日上限 | `L_daily` | int | `≥0` | 当日可提交的最大数量 |
| 永久上限 | `L_finite` | int | `≥0` | 该补给条目全周期可提交的最大数量 |
| 当日已提交 | `D_today` | int | `0–L_daily` | 交付账本中当日成功提交的数量 |
| 全期已提交 | `D_life` | int | `0–L_finite` | 交付账本中永久提交的数量 |
| 活动预留 | `R_active` | int | `≥0` | 已为未提交交易保留的数量 |
| 当前可预留数 | `A` | int | `0–+∞` | `offer_quantity` 公式使用的库存输入 |

**Output Range:** 非负整数或显式无限。有限/唯一供应的已提交数只根据交付账本计算，不因物品被吃掉、转交、安装、损失或世界节点卸载而返还。

**Example:** 某食物当日上限为 6，已交付 3，另有 1 份在交易中预留，则 `A = max(0, 6 - 3 - 1) = 2`。

### 可堆叠携带容量

The `pack_capacity` formula is defined as:

`F = Σ max(0, S_i - n_j)`

`R = max(0, x - F)`

`K_new = ceil(R / S_i)`（当 `R = 0` 时为 0）

`U_new = K_new × c_i`

`can_pack = (U_cat + U_new ≤ C_cat)`

**Variables:**

| 变量 | 符号 | 类型 | 范围 | 说明 |
|---|---|---|---|---|
| 物品堆叠上限 | `S_i` | int | `≥1` | 具体物品定义的单堆上限 |
| 现有兼容堆叠数量 | `n_j` | int | `1–S_i-1` | 兼容未满堆叠 `j` 的当前数量 |
| 无需新位可容纳数 | `F` | int | `≥0` | 所有兼容未满堆叠的剩余容量总和 |
| 选定打包数量 | `x` | int | `1–待领取数量` | 玩家本次明确选定的数量 |
| 需新建堆叠的数量 | `R` | int | `≥0` | 填充已有堆叠后剩余的物品数 |
| 新堆叠数 | `K_new` | int | `≥0` | 容纳 `R` 所需的新堆叠数 |
| 每个新堆叠占位 | `c_i` | int | `≥1` | 具体物品定义的类别携带位占用 |
| 已占携带位 | `U_cat` | int | `0–C_cat` | 相应类别当前已占用携带位 |
| 类别容量 | `C_cat` | int | `≥0` | 消费品或住所用品类别的可调上限 |

**Output Range:** `can_pack` 为布尔值；实际移动数只能是 0 或完整的 `x`，不允许 `0 < moved < x`。

**Example:** 堆叠上限为 4，现有兼容堆叠数为 3，本次打包 6 份，则 `F = 1`、`R = 5`、`K_new = 2`。若每个新堆叠占 1 位且类别还有 2 位，整批成功；只有 1 位时整批失败。

### 消费品实际效果

The `consumable_effect` formula is defined as:

`a(i,k) = min(E(i,k), max(0, N_max(k) - N(k)))`

`N_after(k) = N(k) + a(i,k)`

`waste(i,k) = E(i,k) - a(i,k)`

`can_consume(i) = (Σ a(i,k) > 0)`

`waste_ratio(i) = Σ waste(i,k) / Σ E(i,k)`（仅当 `Σ E(i,k) > 0`）

**Variables:**

| 变量 | 符号 | 类型 | 范围 | 说明 |
|---|---|---|---|---|
| 物品定义效果 | `E(i,k)` | number | `≥0` | 物品 `i` 对需求 `k` 请求的效果量 |
| 当前需求值 | `N(k)` | number | `0–N_max(k)` | 生存需求系统拥有 |
| 需求上限 | `N_max(k)` | number | `>0` | 生存需求定义拥有 |
| 实际接受量 | `a(i,k)` | number | `0–E(i,k)` | 本次实际写入需求系统的量 |
| 结算后需求 | `N_after(k)` | number | `0–N_max(k)` | 应用实际效果后的需求值 |
| 溢出量 | `waste(i,k)` | number | `0–E(i,k)` | 因上限而未被接收的效果，只用于提示与结算反馈 |
| 总溢出比例 | `waste_ratio(i)` | number | `0–1` | UI 警告的唯一比例口径；分母为该物品所有正效果之和 |

**Output Range:** 每项实际效果位于 `0–E(i,k)`，结算后需求不超过上限。所有实际效果为 0 时拒绝使用并保留物品；至少一项大于 0 时，完整消耗一份或一次剩余使用次数。

**Example:** 测试食物对食物需求的定义效果为 25，当前值为 82，上限为 100，则实际接受 18、溢出 7、结算后为 100，并消耗一份。当前已为 100 时，实际效果为 0，拒绝消费。

### 设施安装进度

The `installation_progress` formula is defined as:

`remaining = P_required - P_current`

`delta = p_item` 当 `0 < p_item ≤ remaining`；若不满足则 `delta = 0`

`P_after = P_current + delta`

`facility_active = (P_after = P_required)`

**Variables:**

| 变量 | 符号 | 类型 | 范围 | 说明 |
|---|---|---|---|---|
| 当前安装进度 | `P_current` | int | `0–P_required` | 住所/设施系统拥有 |
| 激活所需进度 | `P_required` | int | `>0` | 设施定义的完成门槛 |
| 单个组件贡献 | `p_item` | int | `>0` | 兼容组件每单位提供的进度 |
| 剩余缺口 | `remaining` | int | `0–P_required` | 设施距离完成所需进度 |
| 实际进度增量 | `delta` | int | `0–remaining` | 本次真正提交的安装进度 |
| 结算后进度 | `P_after` | int | `0–P_required` | 安装后的设施进度 |
| 设施激活 | `facility_active` | bool | `false/true` | 进度到达门槛时为真 |

**Output Range:** `delta` 为 `0–remaining`；`P_after` 永不超过 `P_required`。设施已完成、物品标签不兼容、物品位置错误、实例已应用或组件贡献超出剩余缺口时，输出增量 0 并保留物品。

**Example:** 设施当前进度为 1，所需进度为 2，兼容组件每个贡献 1，则 `remaining = 1`、`delta = 1`、`P_after = 2`，设施激活，该组件实例转为“已应用”。

所有公式都只使用枚举、数字、布尔值和稳定 ID，不读取 HUD 显示、场景节点、动画完成信号或随机数。每次修改按“读取同版本快照 → 计算完整结果 →
验证所有前置条件 → 一次提交所有领域变化”的顺序执行；提交失败时产生零状态变化。

首轮所有权决策见 [ADR-0009](../../docs/architecture/adr-0009-item-lifecycle.md)：供应与物品账本同属 `ItemState`，
报价校验、预留、创建、扣库存及记录交易在同一同步调用内完成，期间不发信号、不等待网络；没有可跨帧观察或保存的活动预留。
因此公式中的 `R_active` 在命令边界为 0，确切数量仍只提交一次。`GameState` 持有该领域对象，拥有需求、时间及存档；
它在实际场景中再次验证角色安全状态和与命名位置的距离。今后若引入异步预留，必须显式实现本章超时释放规则。

## 边界情况

以下结果都是确定规则，不留给运行时自由推断：

| 情况 | 精确处理 |
|---|---|
| NPC 只说“给你点吃的/零件” | 不创建交易；继续当前会话或免费重试，直到回复具名具体库存物品并通过完成门禁 |
| 对话工作平面先返回成交、NPC 仍在说话 | 保留待提交结果；只有同一 `reply_id` 的语音自然结束后才提交；播放取消、超时、走开或场景卸载均撤销本次待提交结果 |
| 语音不可用、网络失败或未激活 | 仅当运行时给出不可用原因时开放 `gesture_fallback`；玩家明确手势命令使服务点同步交付具体库存物 1 份，随后投影到柜台；不等待不存在的 `reply_id`，普通手势仍为 0 |
| 同一交易完成回调到达两次 | 以交易 ID 查询结算账本；第二次返回首次结果，新增数量为 0，库存不再扣减 |
| 领域实例批量创建失败 | 整批回滚：不写结算账本、不扣库存、不保留部分实例；保留免费重试 |
| 领域交易已提交但世界模型投影失败 | 纯数据仍保持“柜台待领取”且库存已提交；显示通用占位物并重试投影，不撤销 NPC 已完成的交付、不复制实例 |
| 柜台同时存在两笔待领取交易 | 分别保留来源交易和物品身份；玩家逐笔处理，不合并不同规则的实例 |
| 场景卸载时仍有柜台待领取物 | 保存为该服务点的待领取记录；重载时在合法交付位重建，不退库存、不复制 |
| 服务点日切时仍有待领取物 | 旧物继续存在且计入已提交供应；日切只重置每日库存账本，不删除或重复补发旧物 |
| 玩家选打包两份但容量只够一份 | 整次打包失败，移动 0 份；界面提示可改选一份或先腾出对应类别携带位 |
| 玩家在容量检查后、提交前失去空位 | 用同一版本号重新验证；验证失败则移动 0 份，物品仍在柜台 |
| 两份食物选择“一份吃、一份带” | 先对所选一份做消费事务，再对另一份做打包事务；任一步失败只回滚该步，未处理物仍留在柜台 |
| 所有需求效果均为 0 | 禁止消费且不扣物品；若至少一项有效则消费一份，并在确认前显示溢出提示 |
| 使用动作开始后被昏倒、日切或模态界面打断 | 若领域事务尚未提交，效果与扣物均为 0；若已原子提交，则保留完整结果，不重复播放也不再次结算 |
| 在对话、录音、奔跑或跳跃时使用随身食物 | 拒绝命令并保留物品；玩家回到安全非对话状态后可立即重试 |
| 日常用品在野外被选中 | 只显示“带回住处”及兼容位置提示，不提供“使用”；不得产生被动效果 |
| 日常用品放到错误位置或已满位置 | 放置失败，实例仍在携带位，住所及已有物品不变，不自动交换 |
| 拆下生效中的耐用品但携带位已满 | 禁止拆下；效果与物品位置均保持原样，不把物品丢到地面 |
| 安装组件贡献大于设施剩余缺口 | 安装失败并保留组件；需求封顶型供给应提前避免生成这种无用组件 |
| 设施已完成但旧交易仍承诺组件 | 库存/成交门禁返回不可交付；若历史待领取实例已合法存在，则允许领取但不可安装，可按白名单转交或保留，不复制设施效果 |
| 昏倒时没有可损失普通物品 | 只结算既有的时间与需求后果，物品损失数为 0；不得改丢保护物或住所物品 |
| 昏倒与使用同帧发生 | 游戏状态先锁定领域操作顺序：已提交的消费先保留，再从提交后的携带快照选损失物；未提交的消费先取消，再结算损失 |
| 保存发生在交易预留但未提交期间 | 不把短生命周期网络预留写成玩家物品；载入后由服务点按超时规则释放预留，结算账本保持未完成 |
| 载入时世界节点或住所位置尚未就绪 | 先恢复纯数据记录；表现层在对应场景/位置注册后投影，期间不得把物品迁到背包或标记丢失 |
| 旧档同时有资源计数和已恢复需求 | 资源计数迁移为打包物品，需求值原样保留；迁移本身不调用使用效果，也不重复修复设施 |
| 玩家观察 NPC–NPC 对话时服务交易也在进行 | 两套流程各自推进；词汇只按观察事件进入 `heard`，物品只按成交门禁结算，任一结果不得触发另一套奖励 |

## 依赖

### 硬依赖

| 依赖系统 | 必须提供的契约 | 本系统不接管的职责 |
|---|---|---|
| 游戏状态与时间 | 当前日/领域时间、操作顺序、昏倒与日切事件、版本化状态提交 | 时间流逝、需求衰减、通关节奏 |
| 世界交互接口 | 稳定交互体 ID、可用动作查询、动作意图转发、场景注册/卸载事件 | 输入判定、距离判定、世界节点生命周期 |
| NPC 服务对话 | 通过四层成交门禁的不可变交易结果；唯一交易 ID；具体库存物品和确切数量 | 转写、发音/地道度评分、档位计算、NPC 台词和语音播放 |
| 服务点库存 | 每项物品的供应策略、原子预留/提交/回滚、唯一键 | 玩家物品实例和使用效果 |
| 生存需求 | 需求当前值/上限、原子应用效果并返回实际接受量 | 消费品库存、动画、使用地点规则 |
| 住所与设施 | 玩家住所身份、命名位置、兼容标签、占用、设施进度及效果提交/撤销 | 携带容量和物品生命周期 |
| 保存与继续 | `SAVE_VERSION`、纯数据序列化、迁移入口、事务账本持久化 | 物品规则判断和表现节点保存 |

### 软依赖

| 依赖系统 | 用途 | 缺失时的降级 |
|---|---|---|
| HUD 与反馈 | 柜台选择、临时物品条、容量/浪费/失败提示 | 仍可由无界面命令完整测试；正式玩家构建不得缺失 |
| 音频与无障碍 | 拿取、包装、进食、放置与安装反馈；字幕/非颜色提示 | 保留动作和视觉状态，不阻断领域结算 |
| 任务与 NPC 关系 | 白名单转交、可选互动结果 | 禁用转交动作，不影响吃喝、住所与三夜通关 |
| 词汇系统 | 无数据依赖，仅共享场景与输入优先级 | 完全独立运行；物品系统不创建任何词汇事件 |

依赖方向必须保持为“对话/库存产生交易 → 物品保存实例 → 需求或住所接收效果”。需求、住所、HUD 和世界节点
不得反向直接创建物品。Godot 实现不得让场景节点成为存档源；若现有 `GameState` 同时承载资源计数、需求和事务，实施前应先
通过架构决策把交易账本、物品实例与表现投影的所有权分清，再迁移旧字段。

## 可调参数

下表给出纵向切片推荐基线和安全范围。超出安全范围需要新的平衡验证；标为“逐物品”的值不得被一个全局常量覆盖。

| 参数 | 推荐基线 | 安全范围/约束 | 所有者与影响 |
|---|---:|---|---|
| 消费品携带位 `C_consumable` | 4 位 | 2–8 位 | 物品系统；过低会迫使频繁折返，过高会消除取舍 |
| 住所用品携带位 `C_residence` | 1 位 | 1–2 位 | 物品系统；强调一次带回一件明确用品 |
| 小型消费品堆叠上限 | 每堆 2 份 | 1–4 份，逐物品定义 | 物品定义；须与两档交付保持可读 |
| 每个新堆叠占位 `c_i` | 1 位 | 1–2 位，逐物品定义 | 物品定义；大型用品可占 2 位但不能挤入消费品位 |
| 数量型日常库存 | 每项每日 6 份 | 2–6 份/日 | 服务点库存；必须能兑现一次 `generous` 承诺 |
| 唯一权益库存 | 每唯一键 1 件 | 固定 1 件 | 服务点库存；按“住所 + 物品/位置”建立唯一键 |
| 加热器所需组件 `P_required` | 2 点 | 1–3 点 | 住所设施；当前属于非主线可选互动 |
| 单组件安装进度 `p_item` | 1 点 | `1–P_required` 且不得超过剩余缺口 | 具体组件定义 |
| 昏倒物品损失数量 | 最多 1 个实例/堆叠单位 | 0–1 | 游戏状态；不可扩大到保护物、柜台物或住所物 |
| 浪费警告阈值 | 总溢出比例 ≥25% | 10%–50% | HUD；按 `waste_ratio` 判断，只影响事前提示，不改变结算公式 |
| 临时物品条显示方式 | 按住显示、松开隐藏 | 固定交互原则 | HUD/输入；不得改成常驻资源栏 |
| 消费品效果 `E(i,k)` | 逐物品设置 | `≥0`，至少一项正值；三日最低档路径可通关 | 物品定义 + 生存平衡；不可按交付档位放大单份效果 |
| 食物腐坏 | 关闭 | 纵向切片固定关闭 | 范围约束；若未来开启需新设计库存、时间和提示规则 |

调参顺序固定为：先保证无语音 `fallback` 与 `sparse` 路径可以在合理往返次数内连过三夜，再验证 `generous` 只减少
资源压力而不产生无效重复物，最后才微调携带容量和浪费提示。不得用提高单份效果来补偿交易数量或库存实现错误。

## 视觉与音频要求

表现目标是让资源成为“已经交到玩家手上、能被安排的东西”，而不是掉落光柱、货币飞字或抽象数值弹跳。
物品外形、材质和色彩遵循 Art Bible：食物/饮品使用柔和有机轮廓与包裹结，住所用品与安装组件使用更明确的结构轮廓、
合金齿口或维护标记；可交互态除颜色外还必须有轮廓、图标或姿态差异。

| 事件/状态 | 必需视觉反馈 | 必需音频反馈 |
|---|---|---|
| 柜台交付成立 | NPC 把具名物品放到托盘/递交位；物品保持可见，不吸入 HUD | 同轮 NPC 语音先完整结束；随后使用轻微放置声，不盖过台词 |
| 柜台待领取 | 物品处于稳定可辨轮廓，靠近时显示交互图标；无持续闪光 | 无循环提示音 |
| 现场吃/喝 | 手部/物品短动作，物品份数在提交点后减少 | 一次短促材质声；失败或取消不播放完成音 |
| 打包 | 外观增加包裹、瓶盖或携带束带状态；不是物品消失特效 | 布料、纸袋或容器扣合声 |
| 携带选中 | 角色附近或临时物品条显示对应图标/剪影，不产生光柱 | 切换时可有低音量单次触感声，快速滚动须限频 |
| 住所可放置 | 兼容位置显示形状匹配轮廓；不兼容位置显示明确禁用符号 | 兼容/不兼容使用不同短音型，不只靠音高区分 |
| 放置并启用 | 物件先落位，再出现铺好、接合或通电的世界状态变化 | 放置声与启用声分为两个事件，和两步规则一致 |
| 安装完成 | 组件可见地并入设施；设施本体切换为修复状态 | 一次机械接合声；不使用胜利号角或奖励音爆 |
| 使用失败 | 物品与领域状态完全不变；就地出现短提示 | 一次克制的拒绝声，可在无障碍设置中关闭 |
| 保存后重载 | 重建与记录一致的模型、包装、放置和设施状态 | 重载不重播取得、消费或安装音 |

单个手持/柜台物品建议不超过 1 个材质、1 张小型图集和 1 个简短状态动画；住所耐用品可有“已放置/已启用”两个状态，
安装设施可有“不完整/完成”两个状态。所有效果必须适配 Godot `gl_compatibility` 与 60 FPS 目标；禁止粒子雨、全屏闪白、
长尾循环高光和依赖后处理才能识别的状态。实现前应为首批具体物品另开资产规格，锁定尺寸、轮廓、材质、手持锚点、住所锚点和 LOD。

## UI 要求

1. **不增加常驻背包栏。** 平时 HUD 继续只显示生存需求和当前情境反馈；按住“物品”输入才展开临时物品条，松开即关闭。
2. **柜台选择。** 交付物出现后，界面在物件附近显示具体名称、剩余份数和合法动作。食物/饮品提供“现场吃/喝”和“打包”；
   日常用品只提供“打包”。两份交付必须允许分别处理，并清楚显示本次选定数量。
3. **临时物品条。** 按类别分组显示消费品与住所用品；每项显示具体图标、名称、数量/剩余次数和当前是否可用。切换选择不暂停世界，
   但对话、录音、模态界面、昏倒和日切会关闭物品条并取消未提交使用意图。
4. **情境动作。** 安全状态中选中食物/饮品时显示“食用/饮用”；日常用品在野外只显示“带回住处”。进入自己的住处后，
   兼容位置显示“放置”，已放置物再根据定义显示“铺好/启用/安装/收回”。非法动作不占据主按钮。
5. **确认与警告。** 全部效果为零时直接阻止并说明“现在不需要”；部分溢出达到阈值时，在扣物前给出一次可取消确认；
   容量不足必须显示缺少哪一类、多少携带位，并提供改小数量的入口。
6. **反馈优先级。** `玩家–NPC 语音会话 > 阻塞性系统事件（昏倒/日切） > 世界交互 > 临时物品条 > 常驻 HUD`。
   较高层出现时关闭或压低较低层，不得让物品条截获柜台对话的录音键。
7. **输入等价。** 键鼠与手柄都必须能完成打开、选择、确认、取消、分份、放置和使用；所有动作可重映射。按住行为必须有
   独立的切换模式选项，避免运动或握持障碍玩家持续按键。
8. **可读性与无障碍。** 在 1152×648 最小验证分辨率和 150% UI 缩放下不得裁切核心动作；状态不能只靠颜色，图标配文字标签；
   提示支持屏幕阅读顺序，音效不是唯一反馈；减少动态模式下用淡入/状态切换替代弹跳和位移动画。
9. **状态所有权。** UI 只发送意图并展示领域返回值。关闭菜单、换场景、改分辨率或控制器断连都不得改变物品数量、位置或使用状态。

这些界面超出现有轻量 HUD 的既定范围。进入实现拆分前，必须以本章为输入补一份独立 UX 规格，明确柜台分份、临时物品条、
住所放置和手柄焦点流；UX 文档不得改写本 GDD 的状态与结算规则。

## 验收标准

### 成交与交付

1. **四层成交门禁（自动化）**
   Given 服务端、Godot 对话服务、场景 Runner、游戏状态中任一层缺少“具体库存物品、具名交付承诺、完成行为、同一 `reply_id`
   播放完成”之一，When 尝试提交语音交易，Then 物品实例、库存提交、交易账本、需求和住所状态均不变化。
2. **拒绝泛类与错误承诺（自动化）**
   Given NPC 只说 food/snack/parts 等泛类词、使用问句、承诺库存外物品或具名物品与交易物品不一致，When 回复结束，Then 不创建交易且玩家可免费重试。
3. **音频完成门禁（自动化）**
   Given 具名承诺与完成行为已到达但同一 `reply_id` 仍在播放，When 查询状态，Then 物品与账本不变；When 音频自然结束，Then 才原子创建交易结果。
4. **兜底等价门禁（自动化）**
   Given 运行时明确标记语音不可用、网络失败或未激活，When 玩家明确使用 `gesture_fallback` 触发同步柜台交付，Then 创建确切 1 份；
   Given 语音能力可用或只是普通手势，Then 创建 0 份。
5. **确切数量为唯一来源（自动化）**
   Given 合法库存预留与交易均为 1 且 `band=generous`，When 结算，Then 只创建 1 份，不按档位再次扩为 2；Given 预留缺失、
   交易数量与预留不一致或超过档位上限，Then 创建 0 份、回滚预留并记录协议错误。
6. **无直接数值效果（自动化）**
   Given 合法交易成功，When 物品进入“柜台待领取”，Then 需求、住所设施、关系与 `heard/spoken/used` 状态逐位不变。
7. **幂等与整批原子性（自动化）**
   Given 同一交易 ID 提交两次，When 第二次到达，Then 返回首次结果且新增物品和库存扣减均为 0；Given 批量领域实例创建失败，Then 整批新增、库存提交和账本写入均为 0。
8. **表现投影失败（自动化 + 手测）**
   Given 领域交易已经提交，When 柜台模型加载失败，Then 待领取记录与库存提交仍有效、只出现可交互占位表现；When 模型随后可用，Then 原实例被投影且不重复取得。

### 取得、携带与使用

9. **类别动作白名单（参数化自动化）**
   Given 五类物品各一件，When 查询柜台、野外与住所动作，Then 只返回类别默认且被具体物品定义允许的动作，未声明动作一律不可执行。
10. **两份食物分别处理（自动化 + 手测）**
    Given 柜台有同款食物 2 份，When 玩家选择吃 1 份、打包 1 份，Then 需求只结算一次、携带增加 1 份、柜台余量为 0；任一步失败只回滚该步。
11. **打包没有效果（自动化）**
    Given 可打包食物或饮品，When 从柜台移入携带位，Then 需求、关系、词汇与住所状态均不变化。
12. **安全状态限制（参数化自动化）**
    Given 玩家不处于 `idle/walking + 双脚着地 + 无高优先级交互`，When 使用携带消费品，Then 命令被拒绝且物品与需求不变；
    Given 条件全部满足，Then 可同步完成一次事务并触发短动作反馈；动画不承担结算门禁。
13. **消费效果与溢出公式（自动化）**
    Given 效果 25、当前需求 82、上限 100，When 消费，Then 实际增加 18、溢出 7、结果 100 并消耗 1 份；Given 当前值 100，Then 拒绝并保留物品。
14. **浪费警告口径（自动化）**
    Given 物品所有正效果合计 40、总溢出 10、阈值 25%，When 玩家确认消费前，Then 显示一次可取消警告；Given 比例低于阈值或总定义效果为 0，Then 不计算除零且不显示该警告。
15. **纵向切片无腐坏（自动化）**
    Given 打包食物跨越日切并保存载入，When 比较记录，Then 数量、效果、品质与可用性不因时间变化。
16. **住所用品先放后用（自动化 + 手测）**
    Given 玩家在野外携带毯子或零件，When 查询动作，Then 无“使用”且无被动效果；When 在自己的住处放入兼容命名位置，Then
    先进入“住处已放置”，再次执行铺好、启用或安装后才改变住所/设施。
17. **错误位置与原子收回（自动化）**
    Given 位置不兼容、已满或被占用，When 放置，Then 物品仍在携带位且住所不变；Given 生效耐用品允许拆下但携带位已满，When 拆下，Then 效果、位置和物品均不变。
18. **安装进度公式（自动化）**
    Given `P_current=1`、`P_required=2`、`p_item=1`，When 安装，Then `delta=1`、设施激活且组件进入“已应用”；Given 设施已完成、
    组件不兼容、实例已应用或贡献大于剩余缺口，Then `delta=0` 且组件保留。

### 容量、库存与奖励

19. **堆叠容量公式（自动化）**
    Given 堆叠上限 4、现有兼容堆叠数量 3、选定打包 6 份，When 类别剩余 2 位，Then `F=1、R=5、K_new=2` 且整批成功；When 只剩 1 位，Then 移动 0 份。
20. **堆叠兼容与类别隔离（自动化）**
    Given 两件物品任一在 ID、剩余次数、品质、保存状态或使用规则上不同，When 打包，Then 不合并；消费品空位不得用于住所用品，反之亦然。
21. **容量版本重验（自动化）**
    Given 容量检查通过后、提交前被另一事务占用空位，When 提交，Then 版本校验失败、移动 0 份且物品仍在柜台。
22. **库存公式（参数化自动化）**
    Given 每日上限 6、当日已提交 3、活动预留 1，When 查询，Then `A=2`；有限供应永不超过永久上限；唯一交付提交后为 0；显式无限不因提交减少。
23. **供应不因物品去向返还（自动化）**
    Given 有限或唯一物品已经提交，When 随后被消费、安装、转交、损失或卸载，Then 对应永久/唯一供应不增加；跨日待领取物保留，新日只重置每日账本。
24. **奖励方式与单调性（参数化自动化）**
    Given 库存充足，When 输入 `none/sparse/fallback/generous`，Then 数量型为 `0/1/1/2`，唯一权益型为 `0/1/1/1`，高档不小于低档；
    Given `g_required=2、g_current=1、g_committed=0、g_per_item=2`，When 计算需求封顶，Then 意向数量为 0；组件/设施定义若不能
    让全部合法缺口被贡献值整除，Then 数据校验失败且不得进入运行时。
25. **失败档无惩罚（自动化）**
    Given `band=none`，When 完成本轮，Then 创建 0 件、不扣库存、不改变需求、关系或任务，下一轮可免费重试。

### 边界、存档与系统隔离

26. **昏倒损失（自动化）**
    Given 同时存在普通可损失携带物、保护物、唯一物、柜台物和住所物，When 昏倒，Then 只从合法候选中按“优先级 → 取得时间 → 实例 ID”
    选择第一个堆叠并扣 1 个数量单位；没有候选时损失为 0。
27. **转交白名单与范围约束（自动化）**
    Given 物品或目标不在转交白名单，When 转交，Then 物品保留；出售、拆解、通用合成、货币兑换、自由摆放和无限升级动作均不可用。
28. **状态存档往返（自动化）**
    Given 每种非终态、终态、住所生效态及已结算交易各一条记录，When 保存并重载，Then 稳定 ID、数量、状态、来源、位置、剩余次数、
    应用标记和账本逐位一致，且不重播取得、消费或安装效果。
29. **预留与延迟投影（自动化）**
    Given 保存发生在库存预留但未提交阶段，When 载入，Then 不生成玩家物品且预留按超时释放；Given 住所或世界节点尚未注册，Then 先恢复纯数据，注册后再投影，不迁入背包也不标记丢失。
30. **旧档迁移（自动化）**
    Given 旧档含 `berries/scrap/water/heater_repaired` 与已恢复需求值，When 首次迁移，Then 分别映射为 `food_legacy_berries`、
    `component_alloy_part`、`drink_bottled_water` 与已完成的 `facility_home_heater`，需求原样保留；再次载入不重复生成或应用。
31. **词汇系统隔离（自动化）**
    Given 玩家观察 NPC–NPC 对话，When 新词被记录，Then 只由词汇系统触发 `heard`；Given 物品交付、打包或使用事件，Then 这些事件不触发
    `heard/spoken/used`、词级练习或词汇奖励。后续玩家–NPC 真实交流依旧可独立证明 `used`；服务对话期间物品输入不得劫持录音键。
32. **输入等价、无障碍与优先级（自动化 + 手测）**
    Given 同一存档，When 分别用键鼠和手柄完成打开、选择、分份、确认、取消、放置与使用，Then 领域结果一致且动作可重映射；
    Given 1152×648、150% UI 缩放、物品条按住/切换两种模式、关闭音效或启用减少动态，Then 核心动作不裁切、不丢焦点，
    图标与文字均可辨；对话、昏倒或日切出现时关闭物品条并取消未提交意图。
33. **表现不驱动结算（自动化 + 手测）**
    Given 动画、音效或世界节点缺失或延迟，When 领域事务已经提交，Then 不重复或撤销结果；完成音各只播放一次，失败/取消不播放完成音，
    且不使用掉落光柱、全屏闪白或常驻循环高光。
