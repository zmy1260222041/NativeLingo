# G2 语料 —— L2 口音短语录音采集规格

对应 R-14 的 **G2**(`docs/reviews/2026-08-08-survival-game-fit.md` §2)。
量具已就绪:`scripts/game_asr_gate.py`。**语料尚不存在** —— 本文档是采集规格。

## 0. 为什么必须新采,不能复用任何现有数字

**R-10 的 4.01% 归一化 WER 不能用。**那个数字是在 `videos/7.1.mp4`(CBS News)上测的:
演播室音质、母语播报腔、完整句子、无环境噪声。本模块的输入分布是另一件事 —— L2 口音、
2–6 词、语法不全、手机/笔记本麦克风、可能有环境噪声。G2 自己写明**同一个模型在两个
分布上的表现不可互推**。把 4.01% 抄进 G2 行等于没测。

**Piper 合成音也不能用。**`--synthetic-smoke` 存在的唯一目的是证明
`clip → transcribe_waveform → 槽位匹配` 这条链路能跑通。合成语音没有 L2 口音、
没有 disfluency(重启、拖长、犹豫)、没有环境噪声,在它上面测必然给出系统性偏乐观的
数字 —— 那会**悄悄作废这道门**,比不测更糟,因为它看起来像测过了。脚本因此在该模式下
硬编码拒绝输出 PASS,数字一律标注「冒烟,不可回填 R-14」。已实测的冒烟结果是
recall = 1.000(6/6),这个 1.000 正是「合成音测不出东西」的直接证据。

`--dry-run` 同理:它吃预先给定的转写文本,只验打分逻辑,不是测量。

## 1. 规模

G2 判据只点名 **infant / toddler** 两级。规模按「让判据的置信区间窄到能支撑裁决」定,
而不是按「凑个整数」:

| tier | 录音条数 | 说明 |
|---|---|---|
| `infant` | ≥60 | 判据覆盖级,必须单独出数字 |
| `toddler` | ≥60 | 判据覆盖级,必须单独出数字 |
| `youth` | ≥20 | 非判据级,只作分布参照 |
| `professional` | ≥20 | 同上 |

**每级 60 条的来由**:每条 2–3 个期望关键词 → 每级约 150 个关键词观测。在真实召回
0.90 时,150 个观测的 Wilson 95% 下界约 0.84;真实 0.85 时下界约 0.78。也就是说
60 条**刚够区分「稳过」与「贴线」**,再少就只能报 INCONCLUSIVE。脚本的
`--min-clips` 默认 30(infant+toddler 合计),低于它只报 INCONCLUSIVE 而不报裁决 ——
这是脚手架护栏,不是对 G2 阈值的改动。

**说话人**:≥8 人,母语背景 ≥3 种(项目主用户是中文母语者,中文背景应占多数但不能
只有中文 —— 单一 L1 会把结果绑死在一种口音的音系上)。同一说话人在同一级不超过 10 条,
避免个体口音支配统计。性别与年龄尽量分散。

## 2. 说话人该说什么 —— 粗糙学习者形式,不是标准答案

这是本规格最容易做错的一步。**不要让说话人念 `reference_answer`。**
场景的 `reference_answer`(如 "I want bread, please.")是给 §6.4 可选发音轨合成参考音
用的,是标准答法。用它录音测出来的是「母语式完整句子的转写率」,不是 G2 要的东西。

正确做法:给说话人**中文的情境 + 意图**,让他用自己想到的英文说出来,不给英文范例。

```
情境:你饿了。街边有人在分发面包。
你的意图:让对方明白你想要面包。
请用英语说出来 —— 想到什么说什么,不用组织完整句子,说错也不要重录。
```

期望采到的形式(这些才是 delivery 判准链路真实的输入):

- 电报式:`me want bread` / `bread please` / `want eat`
- 语法不全:`I hungry` / `you give me bread?` / `blanket, I cold`
- 带 disfluency:`I... uh... I want, want bread` / `can I... have that... thing?`
- 只有名词:`bread` / `blanket` / `water`
- 中式语序或直译:`I very hungry` / `have no eat`

**明确要保留的**:重启、填充词(uh / um / 那个)、拖长、自我更正、发错的音、
主谓不一致、冠词缺失。这些不是瑕疵,它们就是被测分布本身。

**明确不要的**:念稿、多次重录取最好的一条、录完后剪掉犹豫、说话人事先看过
`accept` 集合(那会污染关键词命中率 —— 他会照着 accept 说)。

## 3. 录音条件 —— 镜像 App 真实采集路径

采集条件必须与 `desktop/src/modules/recording.js` 走 MediaRecorder 的那条路一致,
否则测出来的是「棚里录音的转写率」。

| 项 | 要求 |
|---|---|
| 麦克风 | 笔记本内置麦 / 手机内置麦 / 普通耳机麦。**不用**外接电容麦或声卡 |
| 距离 | 30–60 cm,自然坐姿。不贴嘴、不用防喷罩 |
| 环境 | 三档各约 1/3:安静室内、有背景人声或键盘声的室内、有空调/风扇/交通底噪 |
| 后处理 | **一律不做** —— 不降噪、不归一化、不压缩、不剪裁静音。脚本内部会走 `audio_io.load_audio` 的峰值归一化,与生产路径一致,不要在采集阶段先做一遍 |
| 时长 | 每条 1–6 s(对应 2–6 词加上首尾静音) |
| 采样率 | 采集端 16 kHz 或更高即可;`load_audio` 会重采样到 16 kHz 单声道 |
| 格式 | 优选 `.wav`(PCM 16-bit)。`.flac` / `.m4a` / `.webm` 也能读(soundfile + librosa) |
| 命名 | `{tier}-{scenario}-{speaker}-{seq}.wav`,例 `infant-food-ask-bread-s03-01.wav` |

已知不确定项:MediaRecorder 在 WKWebView 下的实际编码容器与码率(见项目记忆
frontend-recording-playback 一条)会影响转写。**如果能从 App 里直接导出录音,优先用
那条路采集** —— 那才是零偏差的采样。用外部录音工具采集是次优方案,采到的音质会略
偏好于生产。这一点必须在回填 G2 时写明。

## 4. manifest 格式

`manifest.json`(或 `.csv`,同名字段)与 `clips/` 平级:

```json
[
  {
    "clip": "infant-food-ask-bread-s03-01.wav",
    "scenario": "food-ask-bread",
    "tier": "infant",
    "expected_keywords": ["bread", "want"],
    "intended": "me want bread"
  }
]
```

| 字段 | 必需 | 含义 |
|---|---|---|
| `clip` | 是 | 文件名,相对 `--clips` 目录 |
| `scenario` | 是 | `desktop/backend/core/game_scenarios/*.json` 里的 `id` |
| `tier` | 否 | 缺省时从场景取。填了则以 manifest 为准(允许把同一场景当作更高一级测) |
| `expected_keywords` | 是 | 见下 |
| `intended` | 否 | 说话人实际说的粗糙原话。只影响报告可读性,不参与计分,但**未命中明细**靠它才能看懂 |
| `well_pronounced` | **是(2026-08-09 新增)** | 上面 `expected_keywords` 里**人耳判定发音可辨**的子集。见 §4.1 |

### 4.1 `well_pronounced` —— 判据修订带来的新标注义务

G2 判据于 2026-08-09 修订为「**对发音合格的词**的关键词召回 ≥0.85」(用户批准,理由见
评审文档 G2 行)。原因是代理语料实测发现,原口径把两件因果不同的事混成一个数:

| | 成因 | 代理实测召回 | 该不该算仪器的锅 |
|---|---|---|---|
| **(A)** | 说话人**确实没把这个词说出来** | 0.333 | **不该。** 声音里没有那个音,任何模型都听不到 |
| **(B)** | 说话人说清楚了、**仪器没听见** | 0.876 / 0.917 | **该。** 这才是 G2 要度量的 |

不区分二者,判据就变成「要求模型听见没说出来的词」—— 不可满足,还会诱导用「换更大模型」
去追一个物理上限(实测 `base.en`→`small.en` 对 (A) 只从 0.300 到 0.333,对 (B) 才有
0.876→0.917 的真实收益)。

**怎么标**:标注者听录音,对每个已填进 `expected_keywords` 的词判断「**不看上下文、单听
这个词,能不能辨认出它**」。能 → 进 `well_pronounced`;不能(音发错、吞掉、含混到辨认不出)
→ 不进,但**仍留在 `expected_keywords` 里**。

- 说话人清晰说出 "me want bread" → `expected_keywords: [bread, want]`,
  `well_pronounced: [bread, want]`
- 说 "me want b'e..."(bread 的尾音吞掉、听不出是 bread)→
  `expected_keywords: [bread, want]`,`well_pronounced: [want]`
- **不要**用「我知道他想说 bread」来判定 —— 标注者知道情境,模型不知道。凭语境猜出来的词
  必须判为不可辨,否则会把 (A) 类混回 (B) 类,判据修订就白做了。

**可照抄的样例**:`verdict_cases/labelled-full.json` 是一份逐字段写全的 manifest,
(A) / (B) 两类各自的标法都在里面(`intended` 字段注明了每条为什么这么标)。
标注时直接照它的字段结构填。那份文件同时是裁决逻辑的回归 fixture,
`transcript` 是手写的、不对应任何录音 —— 见 `verdict_cases/README.md`。

这一项**建议双人独立标 + 记录一致率**(与 `expected_keywords` 同流程),并把一致率写进
评审文档 —— 它是主观判断,一致率低于约 0.8 时该口径本身就不可靠。

**若目标语料最终没有这项标注**:G2 只能退回合并口径,且**必须同时报告合并数与分层数**,
不得只报有利的那个。`game_asr_gate.py` 此时仍会出裁决,但把口径标注为「**退化**」。

**部分标注比全无标注更糟,脚本因此拒绝出裁决。**只有一部分录音带 `well_pronounced` 时,
判据口径算出来的是**这个自选择子集**上的数字 —— 它看起来跟真判据一模一样,却不是。
`game_asr_gate.py` 在覆盖率不满时返回 `INCONCLUSIVE`(measure 与 `--proxy-corpus` 两条路
都是),同时照上面的要求把合并数与分层数都打出来。**要么全标,要么全不标。**代理语料自带这项标注(speechocean762 有五位专家的词级 accuracy,
本轮以 ≥8/10 为「发音合格」),目标语料没有免费来源。

CSV 里 `expected_keywords` 用 `;` 分隔。

### `expected_keywords` 的填法 —— 最容易搞错的一处

填的是「**这条录音在意思上确实包含、且落在该场景 `slots[].accept` 集合里**的关键词」。
判断依据是**听录音**,不是听转写。

- 说话人说了 "me want bread" → `["bread", "want"]`(两个都在 accept 里)
- 说话人只说了 "bread" → `["bread"]`。**不要**把 `want` 也填上 —— 他没表达请求动作,
  转写漏掉它不是 ASR 的错,填上会把 G1 的判准问题算到 G2 头上
- 说话人说了 "I need blanket, cold" → `["blanket", "cold", "need"]`
- 说话人说了 accept 集合里没有的同义形式(如 "I no eat long time")→ **该条不填这个
  关键词**,但要在 `intended` 里如实记下。这类样本是 **G1 / G3 的输入**(accept 集合
  覆盖不足),不是 G2 的失败

脚本对不在任何 `accept` 里的期望关键词会打警告并按「无槽位归属」计入,便于回头核对
manifest 与场景库哪一边需要修。

标注建议双人独立做、对不上的条目丢弃或第三人裁定。R-14 §4 张力 4 已经点出:标注集
的构造方式本身会左右数字,所以**标注流程要一并记录进评审文档**。

## 5. 候选公开 L2 口音语料 —— 许可状态一律「待核实」

自采 120+ 条是有成本的。以下公开语料**可能**能供一部分,但它们全都不是为本模块的
场景设计的,**没有一份能直接满足 §2 的「按情境自由表达」要求** —— 它们绝大多数是
朗读语料(read speech),说话人在念给定文本。朗读语料能测「L2 口音下的转写率」,
测不到「语法不全 + disfluency」这一半。

因此现实定位是:**公开语料作为口音维度的补充,自采录音仍不可省。**

| 语料 | 内容 | 与 G2 的关系 | 许可 |
|---|---|---|---|
| **L2-ARCTIC** | 24 位非母语者(含 4 位中文母语)朗读 CMU ARCTIC 句子,带音素级标注 | 口音覆盖好、有标注;但是朗读、句子长、非本模块场景 | **待核实** |
| **Speech Accent Archive**(George Mason U.) | 数百种 L1 背景朗读同一段英文 | L1 多样性最好;单一朗读段落,与场景无关 | **待核实** |
| **CMU / ISLE / 各类 L2 学习者语料** | 学习者朗读与部分半自由任务 | 部分含自由表达片段,值得筛 | **待核实** |
| **Common Voice**(含 accent 字段) | 众包朗读,可按 accent 过滤 | 规模大、可筛口音;仍是朗读,且录音条件差异极大 | **待核实** |
| **SpeechOcean762** | 5000 条 L2(中文母语)发音评测语料,带专家打分 | L1 与本项目主用户最匹配,含儿童与成人 | ✅ **已核实 CC BY 4.0**(2026-08-09,OpenSLR SLR101 资源页;注:GitHub 仓库的 `LICENSE` 路径 404,授权依据是 OpenSLR 页面)。**已实测使用**,见 §5.1 |

**许可一律标注为「待核实」是有意的。**结论性的授权判断属于 G4 的邻接关切
(`docs/reviews/2026-08-08-survival-game-fit.md` §2 G4:「授权未核实前不得写进实现
计划」),不在本文档范围内。使用任一份之前需要逐条核对:研究用途 vs 商业分发、
是否允许再分发、是否需要署名、是否允许作为评测集随文档发布数字。项目已有先例
(Piper `libritts_r` 的 CC-BY 4.0 逐条核过并写进 NFR-5),按同一标准办。

注意一个额外风险:**如果只用公开朗读语料出数字,G2 会偏乐观**,理由与 Piper 合成音
同类 —— 朗读语料没有 disfluency、录音条件通常优于手机内置麦。回填时必须分开报
「自采 / 公开语料」两组数字,不要合并成一个。

### 5.1 已实测:speechocean762(2026-08-09)

**跑法**:`game_asr_gate.py --proxy-corpus`。该模式**在代码层面拒绝输出 PASS** ——
代理语料只能证伪,不能证实(理由见脚本 docstring)。

**为什么只能证伪**:代理与 G2 目标分布有三处差异,**三处全都让代理更容易** ——
词汇更常见(代理 `see`/`know`/`four`,本模块要 `bread`/`blanket`/`soap`,其中 25 个
内容词经 G4 实测不在 NGSL 2,809 内)、**照稿朗读**而非自发应答、L1 仅普通话一种。
于是:`recall < 0.85` → 真实语料只会更差 → **FAIL 可靠**;`recall ≥ 0.85` → 对目标
分布无推论力 → **不得算 PASS**。

**样本构造**:2–6 词、`completeness == 10.0`、含 ≥1 个场景 `accept` 内容词,
`random.seed(14)` 抽 300 条 / 416 个关键词观测。**功能词单独剔除** —— `the`/`to`/`you`
占原始观测的 30%,识别难度为零,留着会白送召回率。

**结果**:

| 配置 | 混合口径 | 发音合格词口径(判据) |
|---|---|---|
| `base.en` beam1 + vad(**现行生产配置**) | 0.707 | — |
| `base.en` beam5 + `hotwords` | 0.834 | **0.876** ✅ |
| `small.en` beam5 + `hotwords` | 0.875 | **0.917** ✅ |

**语料存放**:仓库外 `~/Developer/corpora/speechocean762/`(520,810,923 bytes,
SHA-256 `876c34b828c2ebcc35ba2ff1ba5947d50e6b0162fc4a4af91db0942422b3bdd5`)。
**不入 git、不随包、不进产品路径** —— CC BY 4.0 允许再分发,但没有理由把 520 MB
评测语料放进仓库或安装包。

**这不构成 G2 通过。** §1 的 160 条目标语料仍然一条都没有。

```

  manifest.json      待采集
  clips/             待采集(音频不入 git —— 含人声,且体积不适合仓库)
```

## 7. 跑法

```sh
GGML_METAL_NO_RESIDENCY=1 .venv/bin/python -m scripts.game_asr_gate \
    --clips scripts/fixtures/game_asr/clips \
    --manifest scripts/fixtures/game_asr/manifest.json \
    --scenarios desktop/backend/core/game_scenarios \
    --json-out docs/reviews/_r14_g2.json
```

输出:overall 召回、逐 tier 召回(带 Wilson 95% 下界)、infant+toddler 合并的判据口径
数字、以及每条未命中的「期望关键词 vs whisper 实际写成什么」+ 错形汇总 ——
后者直接喂 G2 降级路径 (b)(往 `accept` 补常见转写错形)。

脚本**只算关键词召回,不算整句 WER**,因为 `docs/survival-game.md` §6.1 里下游消费
转写的方式就是对 `accept` 做词边界匹配,匹配用的正则与 `core/scenario.py:223` 同一写法。

改动打分或裁决逻辑后跑一次自检(不加载 whisper、不需要语料、几秒钟):

```sh
.venv/bin/python -m scripts.game_asr_gate --self-test
```

它用 `verdict_cases/` 的四份 fixture 钉住四条裁决分支
(PASS / FAIL / 退化口径 FAIL / 部分标注 INCONCLUSIVE)。四条里有三条的作用是**拒绝
给出数字**,所以一个把 INCONCLUSIVE 悄悄变成 PASS 的回归看起来像进展 —— 这就是它
存在的理由。**自检的数字一律不可回填 R-14**,规则与 `--synthetic-smoke` 相同。
